Platform 已删除 Skills 清理设计规范

  • Date: 2026-05-29
  • Topic: Platform deleted skills cleanup
  • Status: Approved design, spec ready for user review

Summary

为 Platform 页面增加“一键检测并清理已删除 Skills”的能力：当某个 skill 已经不在 Central 技能库中，但仍残留在一个或多个安装平台目录里时，用户可以从 Platform 页面触发扫描，在 Update Center 中预览所有可清理副本，并在确认后直接删除选中的平台副本。

本设计采用“Platform 入口 + Update Center 统一预览/应用”的路线。删除策略为预览确认后直接删除平台副本，不提供备份、不做自动后台清理。

Goals

  • 在 Platform 页面提供明确入口，帮助用户检测当前平台中因 Central 或源仓库删除而残留的 skills。
  • 复用 Update Center 的统一 inventory、决策聚合、批量应用和 partial failure 体验。
  • 默认勾选当前 Platform 的可清理项，同时在预览中展示所有可清理的平台副本。
  • 删除前重新校验 Central 状态、agent 边界和路径安全，避免误删 Central 根目录、插件只读目录或越界路径。
  • 保持 Windows-first 验收思路，同时兼容现有 Local、SSH、WSL active target 抽象。
  • 所有用户可见文案通过 i18n 维护，不在组件中硬编码中英文文本。

Non-goals

  • 不做删除前备份、恢复入口或备份目录生命周期管理。
  • 不自动后台清理，也不在扫描后自动删除所有平台残留。
  • 不追溯远端仓库历史，不尝试判断删除发生在哪个 commit。
  • 不提供把已删除 skill 重新导入 Central 的功能。
  • 不重写现有 Central 删除、平台卸载、重复项扫描的业务逻辑。
  • 不把 plugin readonly 来源当作可清理目标。

Context

当前仓库已经具备 Update Center 基础设施：refresh_skill_update_inventory / get_skill_update_inventory 返回统一 inventory，apply_skill_update_decisions 负责把用户决策应用为更新、导入、删除或去重动作。Platform 页面也已经有类似入口：handleScanDuplicates() 会先 rescan()，再刷新当前平台列表，然后扫描重复项并打开 Update Center 的 duplicates tab。

现有 remoteMissing 语义是“Central 仍有记录，但远端源仓库已经删除该 skill”。用户截图中的目标还包含另一种情况：Central 本地条目已经不存在，但 Platform 中仍显示旧副本。因此需要新增一个更明确的 inventory bucket，避免把“远端缺失”和“平台残留副本”混在一起。

用户确认的产品决策：入口采用 Platform 独立按钮与 Update Center 复用；清理流程必须先预览，再由用户确认；确认后直接删除平台副本，不做备份。

Recommended Approach

推荐新增 deletedPlatformCopies inventory bucket，并通过 Platform 页面按钮触发当前平台范围扫描。扫描结果进入 Update Center 的新 tab：“已删除”。该 tab 展示所有可清理平台副本，默认勾选当前 Platform 的结果，用户可以调整选择后使用既有 Apply All 流程删除。

分类边界 remoteMissing 保持源仓库缺失语义；deletedPlatformCopies 专门表示 Central 已无记录的平台残留副本。
交互模式 Platform 负责发起检测，Update Center 负责预览、选择和批量应用，避免新增一套独立删除弹窗。
删除策略 预览确认后直接删除平台副本；执行前重新校验 Central 不存在和路径位于 agent 根目录内。

Alternatives

Option Why not chosen
Platform 独立弹窗 目标直接，但会重复实现 scan、preview、apply、partial failure 和批量选择逻辑，后续 Central 统一管理也看不到这些结果。
只增强现有 remoteMissing tab 改动较少，但无法表达 Central 已经删除、只剩平台残留副本的场景，会混淆两种不同生命周期状态。
扫描后自动删除 操作不可逆且容易误删，违背用户确认的“Preview first, user chooses”流程。

Design Details

Components and responsibilities

  • PlatformView：在“检测重复”旁新增“检测已删除”按钮，负责当前平台范围的扫描入口、loading 状态和 toast 反馈。
  • updateCenterStore：新增 scanDeletedPlatformCopies(agentIds?: string[])，调用 Tauri 命令并把结果写入 inventory。
  • SkillUpdateInventory 类型：新增 deletedPlatformCopies: DeletedPlatformCopyGroup[]。
  • UpdateCenterDialog：新增 tab，并把新 bucket 计数纳入 tab order、counts 和 empty state。
  • DeletedPlatformCopiesTabPanel：展示 skill、platform、路径列表、Central 已不存在说明，以及默认选择状态。
  • decisionAggregation：新增 deleted copy 的初始状态、计数和 removeDeletedPlatformCopies payload 构建。
  • Rust inventory scan：新增 scan_deleted_platform_copies 命令与 pool-level helper，负责发现 Central 已无记录的平台可写残留副本。
  • Rust apply step：新增 apply_remove_deleted_platform_copies_step，在 apply_skill_update_decisions 的 partial success 框架内执行删除。

Data model

interface DeletedPlatformCopyGroup {
  agentId: string;
  skillId: string;
  skillName: string;
  writablePaths: string[];
}

interface DeletedPlatformCopyRemoval {
  agentId: string;
  skillId: string;
  paths: string[];
}

SkillUpdateDecisions 增加 removeDeletedPlatformCopies: DeletedPlatformCopyRemoval[]；SkillUpdateApplyResult 增加 removedDeletedPlatformCopyPaths: string[]，失败仍进入统一 failures 数组。

Data and control flow

  1. 用户在 Platform 页面点击“检测已删除”。
  2. 前端依次执行 rescan()、getSkillsByAgent(resolvedAgentId)、scanDeletedPlatformCopies([resolvedAgentId])。
  3. 无结果时 toast 提示“没有发现可清理的已删除 Skills”。
  4. 有结果时打开 Update Center 的 deletedPlatformCopies tab，并显示扫描到的可删除路径。
  5. tab 默认勾选当前 Platform 的可删除副本；其他平台副本可见但不默认强制删除。
  6. 用户点击 Apply All 后，前端通过 decision aggregation 生成 removeDeletedPlatformCopies。
  7. 后端执行删除前重新读取 Central skills 与 agent 信息，确保 Central 仍不存在、路径仍在 agent 根目录内、目标不是只读/plugin 来源。
  8. 删除完成后重新加载 inventory，Platform 页面通过现有 refresh/rescan 机制更新显示。

Scan rules

  • 目标 skill id 不在 Central skill id set 中。
  • 候选项属于指定 agent，或当未指定 agent 时属于所有可扫描 agent。
  • 候选路径位于该 agent 的 global_skills_dir 下。
  • 候选项不是 plugin readonly，不是显式 read-only。
  • 候选路径可以是目录或 symlink；文件和越界路径不进入可删除结果。

Apply-time safety checks

  • 如果 Central 中重新出现同名 skill id，则拒绝删除该项并记录 failure。
  • 如果 agent 不存在，则记录 failure。
  • 如果路径不在 agent 根目录内，则拒绝删除并记录 failure。
  • 如果路径已不存在，则视为 no-op success，避免阻塞整批清理。
  • Local 使用本地文件系统删除；SSH / WSL 使用 active target 的 remote remove tree 能力，避免写死 Windows 本地路径。

i18n keys

  • platform.scanDeleted、platform.scanningDeleted
  • platform.deletedNone、platform.deletedFound、platform.deletedScanError
  • central.updateCenter.tabs.deletedPlatformCopies
  • central.updateCenter.deletedPlatformCopies.*

Risks

  • 误删非管理目录：通过 agent 根目录边界校验、Central 重新出现校验、readonly/plugin 过滤和执行前二次检查缓解。
  • 分类名称混淆：UI 文案应明确显示“Central 已不存在的平台副本”，避免用户误以为这是远端更新或重复项。
  • 远程 target 行为差异：删除实现必须复用 active target 现有路径删除能力，并为 Local 与 remote helper 分别覆盖测试。
  • inventory 复杂度上升：新增 bucket 要集中接入 counts、decision aggregation 和 apply result，避免散落在组件内形成平行状态。
  • 用户误操作：不提供自动删除；所有删除必须经过 Update Center 预览与用户确认。

Test/Acceptance Criteria

Rust acceptance

  1. Central 不存在、Platform 有可写 copy 时，扫描返回可清理项。
  2. Central 存在同 id skill 时，扫描不返回该项。
  3. plugin readonly 或 read-only path 不进入扫描结果。
  4. 删除路径越界时返回 failure，不删除任何越界路径。
  5. 删除执行前 Central 重新出现时返回 failure。
  6. 路径已不存在时不阻断整体 apply。

Frontend acceptance

  1. Platform 按钮扫描无结果时显示 info toast，不打开无意义的批量删除确认。
  2. 扫描有结果时打开 Update Center 新 tab。
  3. 新 tab 默认勾选当前 Platform 的副本，同时展示其他可清理平台副本。
  4. buildDecisions 能生成 removeDeletedPlatformCopies payload。
  5. partial failure 显示成功数与失败数，并保留失败详情。
