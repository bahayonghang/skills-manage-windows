# Skill Protocol Research

> **Date:** 2026-04-09 · **Status:** historical · **Source:** `docs/research-report.md`

Before settling on the SkillPort skill format, the team surveyed how existing AI agent ecosystems describe a "skill". The conclusions still drive the current Skill Protocol.

## What "Skill" Already Means

| Source | Shape |
| --- | --- |
| [Anthropic Agent Skills](https://github.com/anthropics/agent-skills) | Directory + `SKILL.md` with frontmatter |
| Claude Code marketplace plugins | Plugin manifest pointing at one or more skill directories |
| Codex CLI / Cursor / Gemini CLI | Read shared `~/.agents/skills/` |
| Custom vendor agents | Each picks a subdirectory under `~/.<vendor>/skills/` |

The shapes are isomorphic at the file system level — every ecosystem uses a directory with a top-level markdown file. Differences are in:

- Where the directory lives.
- What metadata the frontmatter carries.
- Whether peers under the directory are surfaced to the agent.

## Adopted Conventions

SkillPort adopted Anthropic's open pattern verbatim:

- `SKILL.md` is the entry file.
- Frontmatter is YAML with `name`, `description`, plus optional `version` / `tags` / `author` / `homepage`.
- Peer directories (`reference/`, `scripts/`, `assets/`) are passed through as-is.

See [Reference → Skill Protocol](../reference/skill-protocol.md) for the live spec.

## Rejected Alternatives

| Considered | Reason for rejection |
| --- | --- |
| Single-file `.skill.md` (no directory) | Loses peer assets that real skills depend on |
| TOML frontmatter | YAML is the established convention; switching would break ecosystem skills |
| Required `version` field | Many community skills omit it; making it required breaks them |
| JSON manifest sibling | Doubles the source of truth for metadata |

## Storage Decisions

SkillPort persists three views of every skill:

```text
┌─────────────────────────┬─────────────────────────────────────────┐
│ View                    │ Source                                  │
├─────────────────────────┼─────────────────────────────────────────┤
│ Central canonical       │ ~/.skillsmanage/skills/<id>/            │
│ Platform install        │ ~/.<platform>/skills/<id>/  (symlink)   │
│ DB row (skills table)   │ Mirror of frontmatter + canonical_path  │
└─────────────────────────┴─────────────────────────────────────────┘
```

The DB row is what the UI binds to. Re-scans reconcile the row with disk truth. Conflicts resolve toward disk: if the row says `description = "old"` but the file says otherwise, the file wins.

## Open Questions in 2026-04-09

- Should AI-generated tags be stored on the skill directory (frontmatter writes) or only in the DB? **Resolution:** DB only; SkillPort never rewrites a user's SKILL.md.
- Do collections need a stable export format? **Resolution:** Yes — see [State Import / Export](../reference/state-import-export.md).
- Should Discover prefer the most-recent SKILL.md when one project has several? **Resolution:** Surface all candidates; let the user pick at import time.
