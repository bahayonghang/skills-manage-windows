# 常青项目审查与五套 harness 对齐改造规划

审查 SkillPort 当前代码、测试与交付工作流，对照 Claude Code、Codex、Grok Build、Kimi Code、Oh My Pi（OMP）的能力边界，形成用户可批准的分优先级改造计划。当前阶段仅授权审查、现有测试及规划材料写入。

## Requirements

- R1：依据当前 HEAD 的项目结构、关键源码和现有测试建立审查证据，区分失败、环境阻塞、跳过与未验证事项。
- R2：对每个实际失败追踪责任层与根因，列出最小修复文件、回归检查及执行依赖。
- R3：核对五套 harness 的规则加载、技能、子代理、权限和执行边界，区分工具能力、模型能力、本仓库接线与本机可用性。
- R4：创建父子任务树，逐项指定适用工具、强模型规划/审查职责和可下放给便宜模型的有限执行范围。
- R5：实施批准后，将已验收决策回写项目说明或项目技能库，并标明适用工具；批准前不修改产品代码、现有规则或共享知识库。

## Acceptance Criteria

- [ ] AC1（R1）：审查报告包含基线提交、关键路径和命令结果，测试通过不能替代外部交付证据。
- [ ] AC2（R2）：每项拟修改内容都有根因依据、具体文件和可判定的检查；未定位原因不得声称已确诊。
- [ ] AC3（R3, R4）：五套工具均有官方来源与本地接线证据；本轮规划交付时父子任务保持 planning 并通过结构与独立审查。批准后的实施状态遵循正常生命周期，最终验收不要求仍为 planning。
- [ ] AC4（R5）：实施后回写已批准、已验证内容及工具适用范围，未批准项不落入执行或全局记忆。
